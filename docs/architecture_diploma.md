# Архитектура программного продукта `my.inventory`

## 1. Назначение системы

Программный продукт `my.inventory` предназначен для автоматизации учета товарно-материальных ценностей предприятия, закрепления оборудования за сотрудниками, оформления возвратов и передач, проведения инвентаризационных сверок и ведения истории операций. Система ориентирована на внутреннее использование в организации и поддерживает как пользовательские, так и административные сценарии работы.

Дополнительно в системе реализованы:

- формирование PDF-отчетов по истории операций и передаче ТМЦ;
- ведение справочников отделов и локаций;
- назначение отдела и локации конкретным сотрудникам;
- журналирование ключевых действий пользователей.

## 2. Общий архитектурный подход

С технической точки зрения `my.inventory` представляет собой веб-приложение на платформе Django. Архитектурно система построена как модульный монолит (`modular monolith`), то есть приложение развертывается как единая система, но внутри разделено на логически самостоятельные доменные модули.

Для проекта выбран именно такой подход, поскольку он:

- упрощает разработку и сопровождение;
- обеспечивает единое хранилище данных;
- уменьшает сложность межмодульного взаимодействия;
- позволяет развивать систему без перехода к избыточно сложной микросервисной архитектуре.

С точки зрения архитектурного стиля система сочетает:

- клиент-серверную архитектуру;
- многослойную архитектуру;
- модульную организацию прикладной логики.

## 3. Клиент-серверная модель

Система функционирует по классической клиент-серверной модели:

- пользователь работает через веб-браузер;
- браузер отправляет HTTP-запросы серверной части;
- сервер обрабатывает запросы, выполняет бизнес-логику и обращается к базе данных;
- результат возвращается пользователю в виде HTML-страниц или PDF-документов.

Таким образом, клиентская часть отвечает за отображение интерфейса, а серверная часть концентрирует правила обработки данных, разграничение доступа и бизнес-операции.

## 4. Многослойная архитектура

Внутренняя организация `my.inventory` основана на разделении ответственности между несколькими слоями.

### 4.1. Слой представления

Слой представления включает:

- Django `views`;
- HTML-шаблоны;
- формы `forms.py`;
- статические ресурсы: CSS, JavaScript, изображения;
- генерацию пользовательских PDF-отчетов.

Этот слой отвечает за прием запросов, валидацию входных данных, вызов прикладной логики и формирование ответа пользователю.

В системе используется серверный рендеринг страниц через Django Templates. Такой подход удобен для корпоративной информационной системы, так как снижает сложность фронтенда и делает поведение интерфейса более предсказуемым.

### 4.2. Прикладной слой

Прикладной слой реализован с помощью `services.py`, `selectors.py` и специализированных модулей отчетности.

Функции `services.py` содержат бизнес-операции, изменяющие состояние системы, например:

- выдачу ТМЦ сотруднику;
- возврат ТМЦ;
- создание и обработку заявок на передачу;
- фиксацию инвентаризации;
- создание и изменение карточек ТМЦ.

Функции `selectors.py` отвечают за операции чтения и подготовки данных:

- фильтрацию и выборку пользователей;
- выборку ТМЦ;
- построение данных для панели мониторинга;
- подготовку истории операций;
- формирование административных представлений.

Дополнительно прикладной слой включает логику подготовки PDF-отчетов. Для этого используются отдельные функции, формирующие структурированные документы на основании данных предметной области.

### 4.3. Слой данных

Слой данных реализован на основе Django ORM и реляционной базы данных PostgreSQL.

Он отвечает за:

- хранение сущностей предметной области;
- описание связей между сущностями;
- обеспечение ссылочной целостности;
- выполнение транзакционных операций;
- поддержку ограничений и инвариантов системы.

### 4.4. Инфраструктурный слой

Инфраструктурный слой включает:

- настройки окружения (`config/settings`);
- Docker и Docker Compose для развертывания;
- Gunicorn в качестве WSGI-сервера;
- WhiteNoise для обслуживания статических файлов;
- health-check endpoints;
- резервное копирование и восстановление базы данных;
- библиотеку `reportlab` для формирования PDF-документов.

## 5. Модульная структура системы

Система разделена на предметные модули, каждый из которых отвечает за отдельную функциональную область.

### 5.1. Модуль `accounts`

Модуль `accounts` реализует работу с пользователями:

- регистрацию и аутентификацию;
- профиль сотрудника;
- административное редактирование учетных записей;
- назначение сотруднику отдела и локации;
- переключение между пользовательским и административным режимами интерфейса.

Ключевая сущность модуля: `User`.

Модель пользователя расширяет стандартную модель Django и хранит служебную информацию о сотруднике: ФИО, телефон, роль, должность, отдел, локацию и другие атрибуты.

### 5.2. Модуль `org`

Модуль `org` отвечает за организационные справочники:

- `Department` — отделы организации;
- `Location` — локации, кабинеты, склады и иные места размещения.

Через этот модуль администратор может создавать и поддерживать справочные данные, которые затем используются при назначении параметров сотрудникам.

### 5.3. Модуль `inventory`

Модуль `inventory` реализует учет самих материальных ценностей.

Его функции:

- создание карточек ТМЦ;
- хранение статуса и местоположения;
- учет серийных и инвентарных номеров;
- назначение периодов инвентаризации;
- хранение результатов сверок;
- хранение фотофиксации.

Ключевые сущности:

- `Asset`;
- `InventoryVerification`;
- `InventoryVerificationImage`;
- `EmployeeInventoryAssignment`.

### 5.4. Модуль `custody`

Модуль `custody` реализует жизненный цикл движения ТМЦ между сотрудниками и резервом.

Основные операции:

- выдача имущества;
- возврат имущества;
- создание заявки на передачу;
- подтверждение или отклонение передачи;
- формирование PDF-отчета по передаче ТМЦ.

Ключевые сущности:

- `AssetAssignment`;
- `TransferRequest`.

### 5.5. Модуль `audit`

Модуль `audit` предназначен для регистрации событий в системе. Он фиксирует:

- выдачу и возврат ТМЦ;
- передачу имущества;
- изменения карточек ТМЦ;
- инвентаризационные операции;
- административные действия, влияющие на бизнес-процессы.

Ключевая сущность: `AuditEvent`.

### 5.6. Модуль `dashboard`

Модуль `dashboard` формирует агрегированные показатели для главной панели:

- общее число ТМЦ;
- число активных закреплений;
- количество передач;
- просроченные сверки;
- назначенные периоды инвентаризации.

### 5.7. Модуль `core`

Модуль `core` содержит общие инфраструктурные элементы:

- базовую абстрактную модель с датами создания и изменения;
- health-check endpoints;
- общие утилиты, включая базовый слой формирования PDF;
- административные команды и служебные механизмы проекта.

## 6. Логическая схема взаимодействия компонентов

Взаимодействие основных компонентов можно представить следующим образом:

```text
Пользователь
   |
   v
Браузер
   |
   v
Django Views + Forms + Templates
   |
   v
Services / Selectors / Reports
   |
   v
Django ORM
   |
   v
PostgreSQL
```

Для отчетных сценариев дополнительно используется отдельная ветка формирования документа:

```text
Запрос на отчет
   |
   v
View
   |
   v
Report builder
   |
   v
PDF response
```

## 7. Основные сущности и связи

Ключевые связи между сущностями системы:

- один отдел может быть назначен многим сотрудникам;
- одна локация может использоваться многими сотрудниками и отделами;
- один сотрудник может иметь множество исторических закреплений имущества;
- одна ТМЦ может иметь только одно активное закрепление одновременно;
- одна ТМЦ может иметь множество заявок на передачу;
- одна ТМЦ может иметь множество записей инвентаризации;
- одна запись инвентаризации может иметь несколько изображений;
- каждое существенное действие может быть отражено в журнале аудита.

## 8. Реализация ключевых бизнес-процессов

### 8.1. Выдача ТМЦ

Выдача ТМЦ реализуется через сервисный слой и включает:

1. проверку отсутствия текущего активного закрепления;
2. обновление статуса ТМЦ;
3. фиксацию локации выдачи;
4. создание записи закрепления;
5. запись события в аудит.

Для защиты от конфликтов используется транзакция базы данных и механизм `select_for_update`.

### 8.2. Возврат ТМЦ

Возврат включает:

1. поиск активного закрепления;
2. завершение закрепления;
3. перевод ТМЦ в резерв;
4. обновление местоположения;
5. журналирование события.

### 8.3. Передача ТМЦ между сотрудниками

Процесс передачи реализован в два этапа:

1. создание заявки на передачу;
2. подтверждение или отклонение заявки.

После подтверждения прежнее закрепление закрывается, создается новое, а пользователь может сформировать PDF-отчет по выполненной операции.

### 8.4. Инвентаризация

Инвентаризационный процесс включает:

1. назначение сотруднику периода инвентаризации;
2. ограничение доступа к сверке по времени;
3. фиксацию факта проверки;
4. прикрепление фото;
5. обновление контрольных дат;
6. запись результата в аудит.

### 8.5. Управление отделами и локациями

Администратор может:

1. создать новую локацию;
2. создать новый отдел;
3. связать отдел с базовой локацией;
4. назначить отдел и локацию конкретному сотруднику.

Этот процесс реализован через отдельный административный экран и используется как часть кадрового сопровождения системы.

## 9. Формирование отчетов в PDF

В системе реализованы PDF-отчеты двух типов:

- отчет по истории операций с ТМЦ;
- отчет по передаче ТМЦ.

Формирование документов выполняется на серверной стороне. Источником данных служат предметные сущности и журнал событий, а результатом является готовый PDF-файл, возвращаемый пользователю в HTTP-ответе.

Такой подход позволяет:

- формировать официальные отчетные документы;
- сохранять единый формат представления данных;
- использовать отчеты в административной и учетной деятельности.

## 10. Безопасность и разграничение доступа

В системе применяются следующие механизмы защиты:

- аутентификация по электронной почте и паролю;
- сессионная авторизация Django;
- разграничение ролей через группы;
- отдельная проверка административного доступа;
- CSRF-защита форм;
- автоматический выход деактивированного пользователя;
- ограничение доступа к административным разделам и отчетам.

Ключевые административные функции, включая управление сотрудниками, отделами, локациями, движением ТМЦ и инвентаризацией, доступны только пользователям с административными правами.

## 11. Развертывание системы

Развертывание `my.inventory` организовано в контейнерной среде Docker Compose. В production-конфигурации предусмотрены два основных сервиса:

- `web` — контейнер с Django-приложением;
- `db` — контейнер с PostgreSQL.

Инфраструктура развертывания поддерживает:

- автоматическое применение миграций;
- сбор статических файлов;
- хранение медиафайлов;
- проверку доступности приложения;
- установку системных шрифтов, необходимых для корректного формирования PDF-документов.

## 12. Обоснование выбранной архитектуры

Выбранная архитектура является рациональной для рассматриваемой задачи, поскольку:

- предметная область естественно делится на отдельные модули;
- модульный монолит проще сопровождать, чем набор микросервисов;
- Django предоставляет готовые средства для ORM, маршрутизации, шаблонов, аутентификации и администрирования;
- PostgreSQL обеспечивает надежное транзакционное хранение данных;
- сервисный подход повышает читаемость и расширяемость кода;
- встроенная поддержка отчетности и справочников делает систему пригодной не только для операционного, но и для административного использования.

## 13. Вывод

Программный продукт `my.inventory` представляет собой модульное веб-приложение с многослойной архитектурой, предназначенное для учета материальных ценностей предприятия. Архитектура системы объединяет клиент-серверную модель, четкое разделение по слоям и логическую декомпозицию по доменным модулям.

Принятая структура обеспечивает надежное хранение данных, прозрачность операций, поддержку отчетности, возможность администрирования справочников и удобное развитие системы в дальнейшем. За счет выделения бизнес-логики в отдельные сервисы, наличия журнала аудита и поддержки формализованных PDF-отчетов система может рассматриваться как полнофункциональная основа для автоматизации учета ТМЦ в организации.
