# Архитектура программного продукта `my.inventory`

## 1. Общая характеристика системы

Программный продукт `my.inventory` предназначен для учета товарно-материальных ценностей предприятия, закрепления оборудования за сотрудниками, оформления возвратов и передач, а также проведения инвентаризационных сверок с фотофиксацией результатов. Система ориентирована на внутреннее использование сотрудниками и администраторами организации.

С технической точки зрения `my.inventory` представляет собой веб-приложение, реализованное на основе фреймворка Django. Архитектурно система построена как модульный монолит (`modular monolith`): все функциональные подсистемы развертываются как единое приложение, но логически разделены на независимые доменные модули.

Такой подход выбран потому, что он обеспечивает:

- простоту разработки и сопровождения;
- единое пространство данных;
- низкие накладные расходы на интеграцию между модулями;
- возможность дальнейшего масштабирования за счет выделения отдельных подсистем при росте нагрузки.

## 2. Архитектурный стиль системы

Архитектура `my.inventory` сочетает признаки клиент-серверной, многослойной и модульной архитектуры.

Система реализует классическую клиент-серверную модель:

- клиентская часть работает в браузере пользователя;
- серверная часть обрабатывает HTTP-запросы, выполняет бизнес-логику и взаимодействует с базой данных;
- обмен данными между клиентом и сервером осуществляется по протоколу HTTP/HTTPS.

На логическом уровне приложение организовано в виде трех основных слоев:

1. слой представления;
2. прикладной слой;
3. слой данных.

Дополнительно выделяется инфраструктурный слой, содержащий механизмы развертывания, журналирования, проверки готовности и настройки окружения.

## 3. Структура модульного монолита

Система разделена на прикладные модули, каждый из которых отвечает за отдельную предметную область.

### 3.1. Модуль `accounts`

Модуль `accounts` отвечает за:

- регистрацию и аутентификацию пользователей;
- хранение учетных данных сотрудников;
- редактирование профиля;
- административное управление пользователями;
- переключение пользовательского и административного режимов интерфейса.

Ключевая сущность модуля: `User`.

Пользовательская модель расширяет стандартную модель Django и содержит дополнительные атрибуты: электронную почту, телефон, должность, роль, местоположение рабочего места, подразделение и аватар.

### 3.2. Модуль `org`

Модуль `org` реализует организационную структуру предприятия. В нем описаны подразделения, к которым могут быть привязаны сотрудники.

Ключевая сущность модуля: `Department`.

### 3.3. Модуль `inventory`

Модуль `inventory` отвечает за ведение карточек ТМЦ и инвентаризационные процессы.

Основные функции модуля:

- создание и редактирование карточек имущества;
- хранение статуса и местоположения ТМЦ;
- назначение периодов инвентаризации сотрудникам;
- фиксация результатов инвентаризации;
- хранение фотоматериалов по сверке.

Ключевые сущности:

- `Asset` — карточка единицы имущества;
- `InventoryVerification` — запись о проведенной сверке;
- `InventoryVerificationImage` — изображение, прикрепленное к сверке;
- `EmployeeInventoryAssignment` — назначение сотруднику периода инвентаризации.

### 3.4. Модуль `custody`

Модуль `custody` реализует процессы движения имущества между сотрудниками и складом.

Основные функции:

- выдача ТМЦ сотруднику;
- возврат ТМЦ в резерв;
- оформление заявки на передачу имущества;
- подтверждение или отклонение передачи.

Ключевые сущности:

- `AssetAssignment` — текущее или историческое закрепление ТМЦ за сотрудником;
- `TransferRequest` — заявка на передачу имущества другому сотруднику.

### 3.5. Модуль `audit`

Модуль `audit` предназначен для регистрации значимых событий системы.

Он фиксирует:

- выдачу и возврат ТМЦ;
- создание и обновление карточек имущества;
- создание, подтверждение и отклонение передачи;
- проведение сверки;
- назначение и отзыв инвентаризации.

Ключевая сущность: `AuditEvent`.

### 3.6. Модуль `dashboard`

Модуль `dashboard` формирует агрегированные показатели для главной страницы системы.

Он предоставляет:

- сводную статистику по имуществу;
- количество активных закреплений;
- перечень просроченных сверок;
- информацию по текущим передачам;
- напоминания о назначенных периодах инвентаризации.

### 3.7. Модуль `core`

Модуль `core` содержит общесистемные элементы:

- базовую абстрактную модель с полями времени создания и изменения;
- служебные точки проверки работоспособности (`health checks`);
- административные команды начальной инициализации.

## 4. Многослойная организация приложения

Внутри каждого доменного модуля используется единый подход к разделению ответственности между слоями.

### 4.1. Слой представления

Слой представления включает:

- Django views;
- HTML-шаблоны;
- формы (`forms.py`);
- статические ресурсы: CSS, изображения, JavaScript.

Этот слой отвечает за:

- прием HTTP-запросов;
- вызов прикладной логики;
- валидацию входных данных через формы;
- формирование HTML-ответа для браузера.

В проекте используется серверный рендеринг страниц с помощью Django Templates. Такой подход упрощает разработку, уменьшает сложность клиентской части и хорошо подходит для внутренней корпоративной системы.

### 4.2. Прикладной слой

Прикладной слой реализован через файлы `services.py` и `selectors.py`.

Функции `services.py` содержат бизнес-операции, изменяющие состояние системы, например:

- выдача имущества;
- возврат имущества;
- создание заявки на передачу;
- подтверждение передачи;
- фиксация инвентаризации;
- создание и обновление карточки ТМЦ.

Функции `selectors.py` отвечают за операции чтения и подготовки данных:

- фильтрацию списков ТМЦ;
- подготовку контекста для административных экранов;
- выборку истории операций;
- построение агрегатов для панели мониторинга.

Такое разделение повышает читаемость кода и упрощает сопровождение: логика чтения данных не смешивается с логикой изменения состояния.

### 4.3. Слой данных

Слой данных представлен моделями Django ORM и реляционной базой данных PostgreSQL.

Модели описывают:

- структуру таблиц;
- типы полей;
- связи между сущностями;
- ограничения целостности.

Примером важного ограничения является запрет на существование более одного активного закрепления одной и той же ТМЦ. Это реализовано через уникальное ограничение для объекта `AssetAssignment` при `is_current = true`.

### 4.4. Инфраструктурный слой

Инфраструктурный слой включает:

- настройки окружения (`config/settings`);
- контейнеризацию через Docker;
- веб-сервер Gunicorn;
- обслуживание статических файлов через WhiteNoise;
- сценарии резервного копирования и восстановления БД;
- механизмы health-check для мониторинга готовности приложения.

## 5. Логическая схема взаимодействия компонентов

Общая схема взаимодействия компонентов может быть представлена следующим образом:

```text
Пользователь в браузере
        |
        v
HTML-страницы / Django Templates
        |
        v
Views + Forms
        |
        v
Services / Selectors
        |
        v
Django ORM
        |
        v
PostgreSQL
```

При выполнении бизнес-операций дополнительно используется модуль аудита:

```text
Бизнес-операция
        |
        +--> изменение основных сущностей
        |
        +--> запись события в AuditEvent
```

## 6. Основные сущности и связи данных

Ключевые связи между сущностями системы можно описать следующим образом:

- один отдел (`Department`) может содержать множество сотрудников (`User`);
- один сотрудник может иметь несколько исторических закреплений имущества (`AssetAssignment`);
- одна ТМЦ (`Asset`) может иметь несколько записей о закреплении, но только одно активное закрепление одновременно;
- одна ТМЦ может иметь несколько заявок на передачу (`TransferRequest`);
- одна ТМЦ может иметь множество записей инвентаризации (`InventoryVerification`);
- одна запись инвентаризации может содержать несколько изображений (`InventoryVerificationImage`);
- один сотрудник может иметь несколько назначений на проведение инвентаризации (`EmployeeInventoryAssignment`);
- каждое значимое действие может порождать одну или несколько записей в журнале `AuditEvent`.

## 7. Реализация бизнес-процессов

### 7.1. Выдача ТМЦ сотруднику

Процесс выдачи реализован в сервисе `issue_asset`.

Основные шаги:

1. проверка отсутствия текущего активного закрепления;
2. изменение статуса ТМЦ на "в эксплуатации";
3. фиксация местоположения имущества;
4. создание записи `AssetAssignment`;
5. запись события в журнал аудита.

Для защиты от гонок данных используется транзакция базы данных и блокировка `select_for_update`.

### 7.2. Возврат ТМЦ

Процесс возврата реализован в сервисе `return_asset`.

Основные шаги:

1. поиск текущего активного закрепления;
2. завершение закрепления;
3. перевод ТМЦ в статус резерва;
4. обновление местоположения;
5. запись события в аудит.

### 7.3. Передача ТМЦ между сотрудниками

Процесс передачи реализован в два этапа:

1. создание заявки на передачу (`request_transfer`);
2. подтверждение или отклонение заявки (`approve_transfer`, `reject_transfer`).

После подтверждения передачи предыдущее закрепление закрывается, создается новое закрепление на другого сотрудника, а в журнал аудита заносится событие завершенной передачи.

### 7.4. Инвентаризация и фотофиксация

Процесс инвентаризации включает:

1. назначение сотруднику периода сверки;
2. открытие доступа к сверке только в разрешенный интервал дат;
3. создание записи `InventoryVerification`;
4. прикрепление фотографии;
5. обновление даты последней и следующей сверки;
6. запись события в журнал аудита.

Таким образом, система обеспечивает не только факт проведения инвентаризации, но и документальное подтверждение результата.

## 8. Подход к безопасности и разграничению доступа

В системе используются следующие механизмы защиты:

- аутентификация по электронной почте и паролю;
- сессионная модель авторизации Django;
- разграничение ролей через группы пользователей;
- отдельная проверка административного доступа;
- автоматический выход пользователя при деактивации учетной записи;
- защита форм с помощью CSRF-механизма Django;
- проверка безопасного URL при перенаправлениях.

В проекте предусмотрены роли `employee`, `inventory_operator`, `department_manager`, `auditor`, `system_admin`. При этом часть административных возможностей дополнительно контролируется через свойство `is_administrator`, которое учитывает как системные флаги Django, так и членство в группах.

Отдельной особенностью интерфейса является поддержка двух режимов:

- пользовательский режим;
- административный режим.

Переключение в административный режим требует повторного подтверждения пароля, что снижает риск несанкционированного выполнения критических операций.

## 9. Развертывание системы

Развертывание `my.inventory` организовано в контейнерной среде Docker Compose.

В состав production-конфигурации входят два основных сервиса:

- `web` — контейнер с Django-приложением, запускаемым через Gunicorn;
- `db` — контейнер с PostgreSQL.

Для системы предусмотрены:

- автоматическое применение миграций;
- сбор статических файлов;
- подключение постоянного тома для пользовательских медиафайлов;
- проверка готовности веб-приложения и базы данных.

Подобная схема развертывания повышает переносимость системы и упрощает запуск приложения в новой среде.

## 10. Обоснование выбранной архитектуры

Выбранная архитектура является обоснованной для данного программного продукта по следующим причинам:

- предметная область хорошо разделяется на независимые функциональные модули;
- система ориентирована на внутреннюю эксплуатацию и не требует сложности микросервисной архитектуры;
- модульный монолит проще тестировать, развертывать и сопровождать;
- использование Django позволяет быстро реализовать надежную серверную логику, формы, маршрутизацию и работу с БД;
- PostgreSQL обеспечивает надежное хранение структурированных данных и поддержку транзакционных операций;
- сервисный подход внутри модулей делает код более поддерживаемым и готовым к развитию.

Таким образом, архитектура `my.inventory` обеспечивает баланс между простотой реализации, надежностью, расширяемостью и удобством сопровождения.

## 11. Вывод

Программный продукт `my.inventory` построен как модульное веб-приложение с многослойной архитектурой. Основу системы составляют специализированные доменные модули, выделенные по предметным областям: учет пользователей, организационная структура, инвентарные карточки, закрепление имущества, аудит событий и аналитическая панель.

Принятая архитектура позволяет централизованно хранить данные, обеспечивать целостность бизнес-процессов, контролировать операции с материальными ценностями и вести прозрачную историю действий пользователей. За счет выделения сервисного слоя, использования транзакций и журналирования событий система обладает хорошей поддерживаемостью и может быть расширена в дальнейшем без кардинального изменения ее основы.
