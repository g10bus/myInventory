# AI Project Overview: `my.inventory`

## 1. Что это за проект

`my.inventory` — это внутренняя корпоративная веб-система для учета товарно-материальных ценностей предприятия, закрепленных за сотрудниками. Проект реализован как серверное Django-приложение с HTML-шаблонами и PostgreSQL.

Основное назначение системы:

- хранение карточек ТМЦ;
- закрепление ТМЦ за сотрудниками;
- возврат ТМЦ в резерв;
- передача ТМЦ между сотрудниками;
- проведение инвентаризаций с фотофиксацией;
- ведение истории операций и аудита;
- административное управление пользователями, отделами, локациями и интеграциями;
- формирование PDF-отчетов;
- аналитика для администратора.

Документ предназначен для другой ИИ, чтобы быстро понять структуру проекта, бизнес-логику и уже реализованный функционал.

## 2. Технологический стек

- Backend: `Python 3.12`, `Django 5.2`
- База данных: `PostgreSQL 16`
- Развертывание: `Docker`, `Docker Compose`
- Статика: `WhiteNoise`
- WSGI: `Gunicorn`
- PDF: `reportlab`
- Интеграция с `1С`: `requests`
- Интеграция с `Active Directory`: `ldap3`

Проект не является SPA. Интерфейс серверно-рендерится через Django Templates.

## 3. Архитектурная модель

Проект построен как `modular monolith`.

Это означает:

- приложение разворачивается как единая система;
- внутри код разделен на предметные `apps`;
- бизнес-логика распределена между `views`, `forms`, `services`, `selectors`, `models`;
- основная часть пользовательского интерфейса реализована на серверной стороне.

Глобальное подключение маршрутов идет через `src/config/urls.py`.

## 4. Основные доменные модули

### `apps.accounts`

Отвечает за:

- регистрацию;
- вход и выход;
- профиль пользователя;
- управление сотрудниками;
- переключение администратора в административный режим интерфейса;
- выдачу и отзыв административного доступа;
- блокировку пользователей.

Ключевая модель:

- `User`

Особенности:

- используется кастомная пользовательская модель;
- возможен локальный вход по email;
- также поддержан вход через `Active Directory`.

### `apps.org`

Отвечает за организационные справочники:

- `Department`
- `Location`

Функциональность:

- создание отделов;
- создание локаций;
- использование этих справочников при управлении сотрудниками.

### `apps.inventory`

Отвечает за учет карточек ТМЦ и инвентаризацию.

Ключевые модели:

- `Asset`
- `InventoryVerification`
- `InventoryVerificationImage`
- `EmployeeInventoryAssignment`

Функциональность:

- создание и редактирование карточек ТМЦ;
- хранение инвентарного номера, серийного номера, статуса и местоположения;
- назначение сотрудникам периодов инвентаризации;
- прохождение сверки с фотофиксацией;
- отображение истории сверок в карточке ТМЦ.

### `apps.custody`

Отвечает за движение имущества.

Ключевые модели:

- `AssetAssignment`
- `TransferRequest`

Функциональность:

- выдача ТМЦ сотруднику;
- возврат ТМЦ;
- создание заявки на передачу;
- подтверждение или отклонение передачи;
- отображение истории операций;
- PDF-отчет по истории;
- PDF-документ по конкретной передаче.

### `apps.audit`

Отвечает за журналирование значимых действий.

Ключевая модель:

- `AuditEvent`

Фиксируются события:

- выдача;
- возврат;
- передача;
- административные действия;
- инвентаризационные операции;
- интеграционные действия.

### `apps.dashboard`

Отвечает за главную панель и аналитику.

Функциональность:

- пользовательская главная страница;
- административный раздел аналитики;
- агрегированные показатели;
- круговые диаграммы, столбчатые графики и тренды.

### `apps.integrations`

Отвечает за внешние интеграции.

Ключевые модели:

- `OneCIntegrationSettings`
- `ActiveDirectorySettings`
- `IntegrationSyncLog`

Функциональность:

- настройка интеграции с `1С`;
- импорт отделов, сотрудников и ТМЦ из `1С`;
- настройка интеграции с `Active Directory`;
- проверка подключения к AD;
- журнал синхронизаций.

### `apps.core`

Инфраструктурный модуль.

Содержит:

- базовые миксины и абстрактные модели;
- health-check endpoints;
- общий PDF-слой;
- часть сквозных тестов и инфраструктурных утилит.

## 5. Роли и модель доступа

В проекте фактически есть два основных режима работы:

- обычный сотрудник;
- администратор.

Обычный сотрудник может:

- войти в систему;
- просматривать свои ТМЦ;
- открывать карточки закрепленного имущества;
- видеть свои инвентаризационные задания;
- проходить сверку в активный период;
- создавать или обрабатывать передачу в рамках доступного сценария;
- смотреть историю операций.

Администратор дополнительно может:

- включать административный режим интерфейса;
- управлять сотрудниками;
- управлять карточками ТМЦ;
- выдавать и возвращать имущество;
- назначать периоды инвентаризации;
- управлять отделами и локациями;
- открывать раздел аналитики;
- настраивать интеграции.

Дополнительные особенности:

- переход в административный режим подтверждается паролем;
- для админских страниц действует ограничение доступа;
- заблокированный пользователь не может войти в систему.

## 7. Ключевые бизнес-процессы

### 1. Выдача ТМЦ

Администратор выдает ТМЦ сотруднику. Создается запись `AssetAssignment`, карточка `Asset` получает статус использования, а локация обычно обновляется по рабочему месту сотрудника. Событие фиксируется в аудите.

### 2. Возврат ТМЦ

Текущее закрепление закрывается, ТМЦ переводится в резерв, обновляется местоположение, операция попадает в историю и аудит.

### 3. Передача ТМЦ

Создается `TransferRequest`. После подтверждения активное закрепление переносится на нового сотрудника. При отклонении исходное закрепление сохраняется.

### 4. Инвентаризация

Администратор назначает сотруднику период инвентаризации через `EmployeeInventoryAssignment`. В активный период сотрудник может пройти сверку по своим ТМЦ. Результат сохраняется в `InventoryVerification`, при необходимости с изображением в `InventoryVerificationImage`.

### 5. История и отчетность

Операции движения имущества отображаются в истории. Для истории и передачи реализовано формирование PDF-документов.

## 11. Важные технические наблюдения

- Это не REST API-проект, а серверный Django-интерфейс.
- Многие бизнес-операции вынесены в `services.py`.
- Чтение и подготовка данных для экранов часто вынесены в `selectors.py`.
- Административный интерфейс реализован не только через встроенный Django admin, но и через собственные страницы управления.
- Система ориентирована на внутреннее корпоративное использование.
- Проект разворачивается через `compose.prod.yaml`.
