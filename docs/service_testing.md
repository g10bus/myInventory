# Тестирование сервиса `my.inventory`

## 1. Назначение тестирования

Тестирование сервиса `my.inventory` выполняется с целью подтверждения корректности работы программного продукта, проверки устойчивости ключевых бизнес-процессов и снижения риска появления ошибок при эксплуатации системы. Для рассматриваемого проекта тестирование особенно важно, поскольку система обрабатывает данные о сотрудниках, товарно-материальных ценностях, операциях выдачи и возврата, передаче ТМЦ, инвентаризационных сверках и внешних интеграциях.

Практическая задача тестирования заключается в том, чтобы убедиться, что пользовательские сценарии выполняются корректно, данные сохраняются без нарушения целостности, а разграничение прав доступа исключает выполнение административных операций обычными пользователями.

## 2. Цели и задачи тестирования

В рамках разработки сервиса были поставлены следующие цели тестирования:

- проверить работоспособность основных пользовательских и административных функций;
- подтвердить корректность бизнес-логики учета ТМЦ;
- убедиться в правильности обработки передачи имущества между сотрудниками;
- проверить механизм инвентаризации и фиксации результатов сверки;
- подтвердить корректность разграничения доступа между ролями;
- проверить работу интеграции с `1С` и `Active Directory`;
- снизить риск регрессий при дальнейшем расширении функциональности.

Для достижения указанных целей решались следующие задачи:

- тестирование регистрации и входа пользователей в систему;
- тестирование операций выдачи, возврата и передачи ТМЦ;
- тестирование отображения истории операций и пользовательских страниц;
- тестирование административных страниц, фильтров и переключения режимов интерфейса;
- тестирование назначения инвентаризационных периодов и фиксации проверок;
- тестирование загрузки данных из `1С`;
- тестирование аутентификации через `Active Directory`.

## 3. Подход к тестированию

В проекте `my.inventory` используется комбинированный подход к тестированию, включающий автоматизированные и ручные проверки.

Автоматизированное тестирование применяется для проверки устойчивых сценариев, которые должны воспроизводиться одинаково при каждом запуске. Такой подход позволяет быстро обнаруживать ошибки после изменения кода и контролировать корректность ключевых бизнес-операций.

Ручное тестирование применяется для визуальной проверки пользовательского интерфейса, компоновки страниц, удобства взаимодействия с формами, а также для приемочной проверки функций, связанных с внешним видом страниц, PDF-документами и пользовательскими переходами.

## 4. Средства и инструменты тестирования

Основным средством автоматизированного тестирования является встроенный тестовый фреймворк Django. В проекте используются классы `TestCase`, которые позволяют выполнять проверки в изолированной тестовой среде и работать с временной тестовой базой данных.

Для тестирования HTTP-сценариев применяется тестовый клиент Django, который позволяет имитировать действия пользователя:

- открытие страниц;
- отправку форм;
- аутентификацию;
- проверку кодов ответа;
- проверку используемых шаблонов;
- проверку содержимого HTML-ответов.

Дополнительно в проекте применяются:

- `unittest.mock.patch` для подмены внешних зависимостей при тестировании интеграции с `1С` и `Active Directory`;
- `SimpleUploadedFile` для имитации загрузки файлов и проверки сценариев фотофиксации;
- проверки моделей и бизнес-сервисов на уровне прикладной логики.

Базовой командой запуска автоматизированных тестов является:

```bash
python manage.py test
```

Для дополнительной технической проверки проекта может использоваться команда:

```bash
python manage.py check
```

## 5. Структура автоматизированного тестирования в проекте

На момент подготовки дипломной работы в проекте реализован набор автоматизированных тестов, охватывающий основные функциональные области системы. Активные тесты сосредоточены в следующих модулях:

- `src/apps/core/tests.py` — 41 сценарий;
- `src/apps/custody/tests.py` — 6 сценариев;
- `src/apps/integrations/tests.py` — 4 сценария.

Таким образом, в системе реализован 51 автоматизированный тестовый сценарий, не считая служебных и исторических `legacy`-проверок.

## 6. Основные группы тестов

### 6.1. Тестирование пользовательских сценариев

В модуле `core` проверяются базовые пользовательские функции системы:

- регистрация нового пользователя;
- вход в систему под учетной записью сотрудника;
- отображение главной страницы;
- просмотр списка закрепленных ТМЦ;
- открытие детальной карточки ТМЦ;
- просмотр истории операций;
- отображение профиля пользователя.

Данные тесты подтверждают, что основной пользовательский контур работает корректно и доступен после авторизации.

### 6.2. Тестирование бизнес-логики движения ТМЦ

В модуле `custody` реализованы тесты, направленные на проверку ключевых операций учета движения имущества:

- выдача ТМЦ сотруднику;
- запрет повторного активного закрепления одной и той же единицы ТМЦ;
- создание заявки на передачу;
- подтверждение передачи ТМЦ другому сотруднику;
- отклонение передачи без изменения текущего закрепления;
- возврат ТМЦ в резерв.

Эти тесты подтверждают корректность изменения статусов, местоположения имущества, текущих закреплений и записей аудита.

### 6.3. Тестирование инвентаризации

Отдельная группа тестов связана с инвентаризационными процедурами. Проверяются:

- назначение периода инвентаризации сотруднику;
- отображение назначенной инвентаризации на панели пользователя;
- запрет прохождения сверки вне назначенного периода;
- возможность прохождения сверки в активный период;
- обязательность фотофиксации при сохранении результатов;
- отображение статуса завершенности инвентаризации в административном разделе.

Такие проверки важны для подтверждения того, что учет ТМЦ сопровождается контролируемой процедурой фактической сверки.

### 6.4. Тестирование административных функций и разграничения доступа

В проекте реализованы проверки административного режима, которые подтверждают:

- доступ администратора к специальным страницам управления;
- недоступность административных разделов для обычного сотрудника;
- корректность фильтрации сотрудников и ТМЦ;
- возможность назначения и отзыва административного доступа;
- блокировку учетной записи пользователя;
- невозможность входа заблокированного пользователя;
- корректность подтверждения перехода в административный режим по паролю;
- доступ администратора к разделу аналитики;
- запрет доступа обычного пользователя к аналитическим страницам.

Данная группа тестов имеет важное значение с точки зрения информационной безопасности и корректного разграничения прав.

### 6.5. Тестирование интеграций

В модуле `integrations` проверяются сценарии взаимодействия сервиса с внешними системами:

- доступ администратора к странице управления интеграциями;
- запрет доступа к странице интеграций для обычного пользователя;
- импорт данных из `1С`, включая отделы, сотрудников и карточки ТМЦ;
- аутентификация пользователя через `Active Directory` с созданием или обновлением локального профиля.

При этом внешние соединения в автоматизированных тестах заменяются объектами-имитаторами, что позволяет проверять прикладную логику без зависимости от реального сервера `1С` или контроллера домена.

## 7. Ручное тестирование

Помимо автоматизированных проверок, для сервиса `my.inventory` целесообразно проводить ручное тестирование. Оно необходимо для оценки аспектов, которые сложно полноценно формализовать автоматическими сценариями.

Вручную рекомендуется проверять:

- корректность визуального отображения страниц на экранах различной ширины;
- удобство навигации по пользовательскому и административному интерфейсу;
- корректность отображения диаграмм, аналитических блоков и фильтров;
- формирование и открытие PDF-отчетов;
- удобство работы с формами передачи, возврата и инвентаризации;
- корректность текстов уведомлений, подсказок и ошибок в интерфейсе.

Результаты ручного тестирования дополняют автоматизированный контроль и позволяют оценить качество системы с точки зрения конечного пользователя.

## 8. Критерии успешного прохождения тестирования

Сервис считается успешно прошедшим тестирование при выполнении следующих условий:

- автоматизированные тесты завершаются без ошибок;
- ключевые пользовательские сценарии выполняются корректно;
- бизнес-логика движения ТМЦ соответствует предметной области;
- ограничения доступа соблюдаются;
- интеграционные механизмы отрабатывают корректно при штатных входных данных;
- ручная проверка не выявляет критических ошибок интерфейса и пользовательских переходов.

## 9. Вывод

Проведенное тестирование сервиса `my.inventory` показывает, что в проекте реализован системный подход к контролю качества. Автоматизированные тесты охватывают основные пользовательские функции, административные сценарии, операции с ТМЦ, инвентаризацию и внешние интеграции. Ручное тестирование дополняет этот набор проверкой интерфейса и пользовательского опыта.

Использование тестов в процессе разработки повышает надежность сервиса, снижает вероятность регрессий и обеспечивает более безопасное развитие программного продукта при дальнейшем расширении его функциональности.
